

# 一、 什么是 RAG ？

## 1.1 RAG 库的优势

### 1.1.1 RAG 库 VS 大模型
大模型有三个天然的缺陷：
| 缺陷 | 说明 |
| :---: | :---: |
| 知识的时效性 | 大模型训练数据有时间边界，最新消息未训练，模型不知道 |
| 大模型的幻觉 | 模型只是在推测接下来什么词出现的概率更高，会编造看似合理实则错误的内容 |
| 知识的边界性 | 训练数据中不会包含未公开且未被平台获取的私人文档 |
### 1.1.2 RAG 库 VS 微调
| 对象 | RAG | 微调 |
| :---: | :---: | :---: |
| 时间成本 | 低，只需重跑向量库 | 高，需要 GPU 重训练 |
| 更新操作 | 主流库可只重跑更改的文档块，几乎实时 | 微小修改也需要重训练 |
| 溯源指向 | 能够精准找出资料原文出处 | 无法溯源，且生成的链接多数无效 |
| 实用场景 | 文档信息检索，知识问答 | 固定格式、身份等，常用于专业领域 |

## 1.2 RAG 库核心思想
> RAG 全称 Retrieval-Augmented Generation，检索增强生成。 RAG 的核心思想：先检索，再生成。先检索库内知识，再拼进 Prompt 里，让 LLM 基于检索内容生成答案。
```bash
用户问题："公司的请假制度是什么？"

没有 RAG：
  LLM → 编造一个看起来合理的请假制度（幻觉），事实上根本没有用户公司内部的文档

有了 RAG：
  用户问题 → 检索知识库 → 找到《XXXX员工手册》第XX章
  → 把原文塞进 Prompt → LLM 基于原文回答（准确）
```

# 二、怎么使用 RAG
RAG 库可以大致分为两个阶段：离线向量库构建和在线大模型问答

## 2.1 向量库的构建 
简单流程为：
```text
┌──────────────────────────────────────────────┐
│             离线阶段：构建知识库             │
└──────────────────────────────────────────────┘
       │
       ▼
文档收集 ──> 文档加载 ──> 文本预处理
                            │
                            ▼
                      文本切分 (Chunking)
                            │
                            ▼
                      嵌入/向量化 (Embedding)
                            │
                            ▼
                      存入向量数据库
```
### 2.1.1 文档加载
支持的文档类型：  

| 类型 | 加载方式 | 注意事项 |
| :---: | :---: | :---: |
| TXT / Markdown |直接读取| 无 |
| PDF |	pdf-parse / pdfjs-dist|	扫描版需要 OCR|
| Word (.docx) |	mammoth / docx-parser| 格式可能丢失 |
| HTML	|cheerio / jsdom	| 需要去标签、去导航 |
| Excel / CSV | xlsx / papaparse| 表格需要转成自然语言描述 |
| 数据库 |	直接查询| 每行转成一段文本 |

### 2.1.2 预处理
简单清洗文本  
eg：
```python
def preprocess(text):
    # 1. 统一换行
    text = text.replace("\r\n", "\n").replace("\r", "\n")

    # 2. 每行去掉首尾空格
    lines = []
    for line in text.split("\n"):
        lines.append(line.strip())
    text = "\n".join(lines)

    # 3. 合并多余空行（3个以上换行变2个）
    while "\n\n\n" in text:
        text = text.replace("\n\n\n", "\n\n")

    # 4. 去掉首尾空白
    text = text.strip()

    return text
```
预处理的核心目标：  
- 去噪：去掉页眉页脚、广告、导航栏等无关内容
- 统一格式：不同来源的文档转成统一的纯文本
- 保留结构：标题、段落边界要保留，后续切分依赖这些

### 2.1.3 文本切分
切分是 RAG 中 **最关键的环节**。切得好，检索精准；切得差，答非所问。  

*为什么不能直接用整篇文档？*
- Embedding 模型有 **token 上限**（通常 512~8192）
- 整篇文档向量化会 **丢失细节**，相似度计算不准
- 检索需要返回 **精确片段**，而不是整本书

### 主流切分策略

#### 2.1.3.1 策略一：固定长度切分（Fixed-size Chunking）
最简单，按字符数切，有重叠窗口：  
```text
chunk_size = 500, overlap = 100

文本: "AAAAAABBBBBBCCCCCCDDDDDDEEEEEE..."

Chunk 1: [0, 500)     → "AAAAAABBBBBB..."
Chunk 2: [400, 900)   → "BBBBBBCCCCCC..."  (与 Chunk 1 重叠 100 字符)
Chunk 3: [800, 1300)  → "CCCCCCDDDDDD..."
```
**优点**：实现简单，chunk 大小可控  
***缺点***：可能在句子中间断开，破坏语义完整性

#### 2.1.3.2 策略二：递归字符切分（Recursive Character Splitting）
LangChain 的默认策略，按分隔符层级递归切分：  
```text
优先级: ["\n\n", "\n", "。", ".", " ", ""]

1. 先用 "\n\n"（段落）切
2. 如果某段太长，用 "\n"（换行）再切
3. 如果还太长，用 "。"（句号）再切
4. 最后按字符数硬切
```
**优点**：尽量保持段落/句子完整性  
***缺点***：chunk 大小不完全可控

#### 2.1.3.3 策略三：语义切分（Semantic Chunking）
根据语义相似度决定在哪里断开：
```text
句子1 → Embedding → vec1 ─┐
句子2 → Embedding → vec2 ─┤ 计算相邻句子的余弦相似度
句子3 → Embedding → vec3 ─┤
句子4 → Embedding → vec4 ─┘

sim(vec1, vec2) = 0.92  → 高，同组
sim(vec2, vec3) = 0.31  → 低！从这里断开
sim(vec3, vec4) = 0.88  → 高，同组

结果: [句子1+句子2] [句子3+句子4]
```
**优点**：语义最完整，检索效果最好  
***缺点***：需要调用 Embedding 模型，成本高、速度慢

#### 2.1.3.4 策略四：结构化切分（Document Structure）
利用文档自身的结构（标题、章节）来切分：
```text
# 第一章 公司简介        ← 一级标题，作为 chunk 边界
我们公司成立于2020年...
目前员工规模...

## 1.1 组织架构          ← 二级标题，继续切分
公司设有以下部门...

# 第二章 规章制度
...
```
**优点**：最符合人类阅读习惯，保留上下文层级  
***缺点***：依赖文档格式规范，非结构化文档不适用

#### 2.1.3.5 切分策略对比
| 策略 | 复杂度 | 语义完整性 | 适用场景 |
| :---: | :---: | :---: | :---: |
| 固定长度 | 低 |	差 | 快速原型、格式混乱的文档 |
| 递归字符 | 中 |	中 | 通用场景，LangChain 默认 |
| 语义切分 | 高 |	好 | 对检索精度要求高 |
| 结构化 | 中 |	好 | Markdown/HTML 等结构化文档 |

#### 2.1.3.6 Chunk Size 怎么选？
```text
太小（<200 tokens）：上下文不完整，回答碎片化
太大（>1000 tokens）：检索不精确，噪声多
推荐：300~800 tokens，overlap 10%~20%
```
经验法则：

- FAQ 类：一个 Q&A 对作为一个 chunk  
- 技术文档：一个函数/一个章节作为一个 chunk  
- 法律合同：一个条款作为一个 chunk
